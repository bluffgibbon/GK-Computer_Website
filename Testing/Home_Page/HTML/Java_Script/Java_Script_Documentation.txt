GK Computer Website
JavaScript Folder Documentation

Last updated: 2026-05-28
Folder: Testing/Home_Page/HTML/Java_Script

====================================================================
1. Executive Summary
====================================================================

This folder contains the client-side behavior for the Testing/Home_Page build of the GK Computer Website. The architecture is mostly modular: component loading, navigation, side menu behavior, consent flow, theme handling, modal interactions, scrolling utilities, and appointment scheduling are each split into focused files.

The primary exception is Home_Java.js. That file is a legacy monolithic bundle that duplicates a large portion of the logic already implemented in the smaller JS_* modules. It should be treated as a refactoring target or compatibility artifact, not as the preferred source of truth.

Current architectural direction:

- JS_Init.js is the intended orchestration layer.
- JS_Loader.js provides reusable HTML fragment loading utilities.
- JS_Navigation.js and JS_Side_Menu.js own the two largest interaction systems.
- JS_Theme.js and JS_Consent.js manage persistent user preferences and first-run gating.
- JS_WhyChooseUs.js owns reusable modal behavior for several content surfaces.
- 05_Flyout_Calendar.js provides the appointment calendar widget.
- Home_Java.js duplicates older versions of several of the modules above.


====================================================================
2. Runtime Architecture
====================================================================

The page is assembled in two layers:

1. HTML fragments are fetched and injected into placeholder containers.
2. After each fragment or fragment group is loaded, the relevant initializer attaches event handlers and runtime behavior.

Primary boot path:

- JS_Init.js waits for DOMContentLoaded.
- JS_Init.js uses loadComponent() and loadSubComponents() from JS_Loader.js.
- Individual modules are initialized only after their required markup exists.

High-level dependency flow:

JS_Init.js
  -> JS_Loader.js
  -> JS_Logo.js
  -> JS_Navigation.js
  -> 04_Flyout_Panel.js
  -> 05_Flyout_Calendar.js
  -> JS_WhyChooseUs.js
  -> JS_Side_Menu.js
  -> JS_Scroll.js

Adjacent but independently loaded behavior:

- JS_Theme.js restores and updates theme state.
- JS_Consent.js uses JS_Theme.js when available.
- JS_Appointment.js exposes a global helper that drives the navigation appointment flyout.


====================================================================
3. Known Architectural Risk
====================================================================

The most important maintenance issue in this folder is duplication.

Home_Java.js contains overlapping implementations for:

- component loading
- navigation behavior
- logo lightbox
- side menu behavior
- scroll helpers
- appointment shortcut behavior
- why choose us modal behavior

Impact of this duplication:

- fixes can be applied in one file and missed in the other
- behavior can diverge across pages depending on which script is loaded
- selectors and positioning logic can drift independently
- theme and consent behavior are not fully represented in the monolith

Recommendation:

- Prefer the modular files as the source of truth.
- Either remove Home_Java.js or document the exact page(s) that still depend on it.
- Do not add new behavior to both implementations unless there is a deliberate compatibility requirement.


====================================================================
4. Load Order and Initialization Responsibilities
====================================================================

JS_Init.js is designed to run after the other modules have been loaded into the page. It coordinates component loading in this order:

1. Top banner
2. Header / brand bar
3. Main navigation shell
4. Navigation sub-components
5. Table of contents
6. Welcome section
7. Why Choose Us section
8. Services section
9. Footer
10. Side menu shell
11. Side menu service sub-components
12. Scroll buttons

Initialization callbacks triggered during that sequence:

- initLogoLightbox()
- initNavigation()
- initFlyouts()
- initFlyoutCalendar()
- initWhyChooseUsCards()
- initGenericModal()
- initSideMenu()
- initSideMenuFlyouts()
- initScrollButtons()
- initSmoothScroll()

Operational constraint:

Many modules assume their DOM exists before they run. If the script load order changes, or if a component file fails to load, the initializer may silently no-op.


====================================================================
5. File-by-File Documentation
====================================================================

--------------------------------------------------------------------
5.1 JS_Init.js
Role: Application bootstrap and orchestration
--------------------------------------------------------------------

Purpose:

- Serves as the page-level startup script.
- Loads HTML fragments in the correct order.
- Ensures initializers run only after the markup they depend on has been injected.

Primary behavior:

- Registers a DOMContentLoaded handler.
- Calls loadComponent() for top-level sections.
- Calls loadSubComponents() for split navigation items and side menu service entries.
- Triggers module-specific init functions after component injection completes.

Important DOM contracts:

- placeholder containers with IDs beginning with Components-
- .main-navigation__list for appended navigation items
- #sideMenu ul for appended side-menu service entries

Engineering notes:

- This is the correct place for orchestration logic.
- Dependency ordering is important. Navigation must exist before navigation init runs. Side menu content must exist before side menu flyout logic runs.
- If a component path changes, JS_Init.js is one of the first files that must be updated.


--------------------------------------------------------------------
5.2 JS_Loader.js
Role: HTML fragment loading utilities
--------------------------------------------------------------------

Purpose:

- Provides the reusable fetch-and-inject helpers used by JS_Init.js.

Functions:

- loadComponent(targetId, filePath, callback)
  Fetches an HTML fragment and injects it into a target element by ID.

- appendComponent(targetSelector, filePath, callback)
  Fetches an HTML fragment and appends it to an existing element selected by CSS selector.

- loadSubComponents(targetSelector, files, done)
  Loads a list of HTML fragments sequentially, preserving order.

Key implementation details:

- Appends a timestamp query parameter to avoid stale caching in local development.
- Uses fetch(..., { cache: "no-store" }).
- Logs failures to the console.

Engineering notes:

- This file is small and clean.
- Equivalent logic also exists in Home_Java.js, which should be avoided.
- There is no retry, fallback, or explicit error UI for failed component loads.


--------------------------------------------------------------------
5.3 JS_Theme.js
Role: Theme persistence and theme button interaction
--------------------------------------------------------------------

Purpose:

- Owns dark/light theme switching.
- Persists theme selection in localStorage.

Functions and top-level behavior:

- setTheme(theme)
  Applies body classes, updates active button state, and saves the choice to localStorage.

- document click delegation
  Handles clicks on .Theme--dark and .Theme--light even if the banner is injected after page load.

- startup restore
  Reads localStorage.theme and reapplies it on script load.

DOM contracts:

- document.body expects .dark and .light classes to have matching CSS behavior
- .Theme--dark and .Theme--light buttons are optional but supported when present

Engineering notes:

- Event delegation is the right choice here because the top banner is loaded asynchronously.
- There is no validation on the saved theme string.
- JS_Consent.js depends on setTheme() if available.


--------------------------------------------------------------------
5.4 JS_Consent.js
Role: First-visit consent and theme selection flow
--------------------------------------------------------------------

Purpose:

- Gates the initial user experience behind a consent overlay.
- Steps the user through terms, privacy, and theme selection.
- Stores completion state in localStorage so the flow only runs once.

Top-level structure:

- Wrapped in an immediately invoked function expression.
- Short-circuits if localStorage.gk_consent_done is already set to 1.
- Registers DOMContentLoaded to wire all consent interactions.

Core responsibilities:

- showStep(id)
  Activates the current consent screen and updates progress indicators.

- completeConsent()
  Writes the consent completion flag, removes preview state, and fades out the overlay.

- applyTheme(theme)
  Uses setTheme() from JS_Theme.js when available, or falls back to directly toggling body classes.

Important DOM contracts:

- #consent-overlay
- .consent-step
- .consent-progress__dot
- #consent-step-label
- button IDs for terms, privacy, theme, and restart actions

Engineering notes:

- This module is not duplicated in Home_Java.js, which means monolithic pages may miss consent behavior entirely.
- The logic assumes all required IDs are present. Missing elements can cause failures when handlers are attached.
- Future policy revisions would likely require versioned consent storage rather than a single binary localStorage flag.


--------------------------------------------------------------------
5.5 JS_Navigation.js
Role: Main navigation system
--------------------------------------------------------------------

Purpose:

- Owns the fixed top navigation bar and its interactive behavior.
- Manages dropdown menus, flyout panels, positioning, and horizontal wheel scrolling.

Primary entry point:

- initNavigation()

Major responsibilities inside initNavigation():

- positionNav()
  Fixes the navigation under the header and recalculates on resize.

- resetNavScroll()
  Resets horizontal nav scroll so the left-most content is visible after layout changes.

- dropdown lifecycle
  Tracks active dropdown state, opens dropdowns on item click, closes on outside click or Escape, and repositions on resize/scroll.

- embedded flyout behavior
  Controls rich flyout panels for dropdown items that expose deeper content.

- horizontal wheel scroll behavior
  Converts mouse wheel input into horizontal movement when the nav is hovered and overflow exists.

Important DOM contracts:

- #header-logo-section
- #main-navigation
- .nav-scroll
- .main-navigation__item--has-dropdown
- .main-navigation__dropdown
- .main-navigation__dropdown-arrow
- .main-navigation__dropdown-item--has-flyout
- .main-navigation__flyout
- .main-navigation__flyout-arrow

Events registered:

- click
- keydown
- resize
- scroll
- mouseenter / mouseleave
- wheel

Engineering notes:

- This is one of the most complex modules in the folder.
- It dynamically moves dropdowns and flyouts to document.body to escape stacking-context issues.
- It is easy to break with CSS or markup changes because the positioning logic relies on precise DOM structure and class names.
- Home_Java.js contains a near-duplicate with slightly different positioning rules. The modular version should be considered authoritative.


--------------------------------------------------------------------
5.6 04_Flyout_Panel.js
Role: Hover-driven navigation flyout management
--------------------------------------------------------------------

Purpose:

- Adds hover-based open/close behavior for navigation flyout panels tied to dropdown items.

Primary entry point:

- initFlyouts()

Core responsibilities:

- Tracks the currently active flyout.
- Positions the flyout directly below the navigation bar.
- Delays hide behavior to allow the user to move the pointer from a menu item to the flyout panel.
- Repositions the active flyout on window resize.

Important DOM contracts:

- #main-navigation
- .main-navigation__dropdown-item--has-flyout
- .main-navigation__flyout
- .main-navigation__dropdown

Engineering notes:

- This file overlaps conceptually with flyout behavior inside JS_Navigation.js.
- That overlap is a design smell because two modules can end up controlling the same flyout surfaces.
- If flyout behavior becomes unstable, this file and JS_Navigation.js should be reviewed together first.


--------------------------------------------------------------------
5.7 05_Flyout_Calendar.js
Role: Appointment calendar widget
--------------------------------------------------------------------

Purpose:

- Renders an inline appointment calendar inside the schedule flyout.
- Allows the user to choose a date and time.
- Synchronizes the selected date into the appointment form.

Primary entry point:

- initFlyoutCalendar()

Core responsibilities:

- Builds a month grid for the current month.
- Marks past dates as unavailable.
- Marks booked dates using an in-memory bookedDates array.
- Populates a time dropdown using a static timeSlots array.
- Handles previous and next month navigation.
- Prevents form and calendar clicks from closing the containing flyout.

Important DOM contracts:

- #flyoutCalendarMonth
- #flyoutCalendarDays
- #flyoutPrevMonth
- #flyoutNextMonth
- #flyoutAppointmentDate
- #flyoutAppointmentTime
- #flyoutAppointmentForm

Engineering notes:

- bookedDates is currently an empty placeholder array.
- timeSlots is hardcoded in the client.
- This implementation is suitable for UI prototyping but not yet for real booking integrity.
- Any production scheduling workflow should source availability and validation from the backend.


--------------------------------------------------------------------
5.8 JS_Logo.js
Role: Header logo lightbox
--------------------------------------------------------------------

Purpose:

- Opens the header logo in a full-screen overlay.

Primary entry point:

- initLogoLightbox()

Core responsibilities:

- Creates the overlay dynamically.
- Clones the logo source into a larger image presentation.
- Opens on click or keyboard activation.
- Closes on overlay click or Escape.

Important DOM contracts:

- .site-header__logo--clickable
- #logo-lightbox-overlay

Engineering notes:

- Overlay styling is embedded directly in JavaScript rather than sourced from CSS.
- Logic is also duplicated inside Home_Java.js.
- If the visual design changes, both the JavaScript and the CSS system should be reviewed together.


--------------------------------------------------------------------
5.9 JS_Scroll.js
Role: Scroll utilities and anchor navigation
--------------------------------------------------------------------

Purpose:

- Provides page scroll helpers.
- Wires the floating scroll buttons.
- Enables smooth scrolling for in-page anchor links.

Primary entry points:

- initScrollButtons()
- initSmoothScroll()

Core responsibilities:

- Scroll-to-top button
- Scroll-to-bottom button
- Dynamic positioning of the bottom button under the navigation bar
- Smooth scrolling for anchor links with href beginning with #

Important DOM contracts:

- #scroll-to-top-button
- #scroll-to-bottom-button
- #main-navigation
- a[href^="#"]

Engineering notes:

- This is straightforward utility code.
- Behavior is also duplicated in Home_Java.js.
- If anchor behavior changes, update both pages that use modular loading and any page still using the monolith.


--------------------------------------------------------------------
5.10 JS_Appointment.js
Role: Programmatic opener for the appointment flyout
--------------------------------------------------------------------

Purpose:

- Exposes a global function that other HTML surfaces can call to jump the user directly into the appointment scheduler.

Primary entry point:

- openAppointmentSchedulerFlyout()

Core responsibilities:

- Locates the navigation item that owns the appointment dropdown.
- Scrolls that item into view.
- Opens the dropdown if it is not already open.
- Opens the appointment flyout trigger inside the dropdown.
- Focuses the first field in the appointment form.

Important DOM contracts:

- #scheduleAppointmentNavItem
- #appointmentSchedulerFlyoutTrigger
- .main-navigation__dropdown
- .main-navigation__flyout
- #flyoutAppointmentForm

Engineering notes:

- This is intentionally global because inline onclick handlers can call it.
- The implementation depends on fixed IDs and timing assumptions.
- The two nested setTimeout calls are practical but fragile. Slow rendering or future animation changes could require adjustment.


--------------------------------------------------------------------
5.11 JS_Side_Menu.js
Role: Side menu and service flyout system
--------------------------------------------------------------------

Purpose:

- Owns the hamburger-triggered side menu.
- Manages service-specific flyout panels attached to side menu items.
- Supports programmatic opening of a service flyout by service key.

Primary entry points:

- initSideMenu()
- initSideMenuFlyouts()
- openSideMenuFlyoutByKey(serviceKey)

Core responsibilities:

- Toggles the side menu open and closed.
- Creates and manages a backdrop.
- Closes the menu on outside click, Escape, or explicit close controls.
- Opens side-menu flyouts for service rows.
- Alternates color classes across items and flyouts.
- Repositions open flyouts on resize.
- Supports service-card click paths that route into the matching service flyout.

Important DOM contracts:

- #sideMenu
- #hamburger-menu_left
- #sideMenuCloseArrow
- .side-menu__item--has-flyout
- .side-menu__flyout
- .side-menu__flyout-arrow
- .service-card[data-service-key]

Engineering notes:

- This is the second major interaction-heavy module in the folder.
- Positioning logic changes based on viewport assumptions.
- Like JS_Navigation.js, it can become brittle when structure or CSS layering changes.
- Home_Java.js contains a similar but not identical implementation.


--------------------------------------------------------------------
5.12 JS_WhyChooseUs.js
Role: Modal system for cards and media
--------------------------------------------------------------------

Purpose:

- Handles expansion of Why Choose Us cards and icons.
- Reuses the same modal container for additional assets, including owner photos, footer images, and service cards.

Primary entry points:

- initWhyChooseUsCards()
- initGenericModal()

Core responsibilities:

- Moves the modal container to document.body to avoid stacking-context issues.
- Clones cards or images into modal-friendly markup.
- Adds accessibility affordances to clickable images.
- Handles modal close behavior.
- Uses event delegation so modal triggers work even for late-injected content.

Important DOM contracts:

- #why-choose-us-card-modal
- .why-choose-us__card
- .why-choose-us__images-row .why-choose-us__icon
- .card-modal__body
- .card-modal__close
- .card-modal__overlay
- .site-header__owner-photo
- .footer__bottom-images img
- .service-card[data-service-key]

Engineering notes:

- This is one of the cleaner modules in the folder and shows good reuse of a single modal surface.
- Cloning DOM is intentional, but cloned nodes will not carry original event listeners.
- A very similar implementation also exists in Home_Java.js.


--------------------------------------------------------------------
5.13 Home_Java.js
Role: Legacy monolithic implementation
--------------------------------------------------------------------

Purpose:

- Attempts to provide a one-file implementation of the page behavior.
- Contains a bundled copy of several modules that are now split into smaller files.

What it duplicates:

- component loading logic from JS_Loader.js
- navigation logic from JS_Navigation.js
- logo lightbox behavior from JS_Logo.js
- side menu behavior from JS_Side_Menu.js
- scroll behavior from JS_Scroll.js
- appointment flyout opener from JS_Appointment.js
- why choose us modal behavior from JS_WhyChooseUs.js

Key concern:

- The file is not an exact mirror of the modular code. There are behavioral differences in positioning, paths, and coverage.

Examples of divergence:

- uses different relative component paths
- uses magic-number positioning for the nav
- does not fully represent the modular theme and consent model
- references initFlyoutCalendar() but does not own the calendar implementation itself

Engineering notes:

- Treat this file as technical debt unless a specific page still requires it.
- If it must remain, document exactly why it exists and which pages still load it.
- The safest long-term direction is to standardize on the modular files and retire the monolith.


====================================================================
6. Cross-File Relationships
====================================================================

JS_Init.js is the coordinator.

- It requires JS_Loader.js to exist first.
- It assumes init functions from the relevant modules are globally available.

JS_Theme.js and JS_Consent.js are loosely coupled.

- JS_Consent.js calls setTheme() if present.
- JS_Theme.js also restores theme independently from localStorage.

JS_Appointment.js depends on navigation behavior.

- It assumes the nav item and flyout structure managed by JS_Navigation.js exists.

JS_WhyChooseUs.js and JS_Side_Menu.js both use event delegation and cloned or moved DOM nodes to work around asynchronous loading and stacking-context issues.

Potential overlap requiring review:

- JS_Navigation.js and 04_Flyout_Panel.js both influence navigation flyout behavior.
- Home_Java.js overlaps with most of the modular files.


====================================================================
7. DOM and CSS Coupling
====================================================================

This JavaScript layer is tightly coupled to CSS class names and HTML component structure.

Common patterns used throughout the folder:

- behavior discovered by specific IDs and BEM-like class names
- classes toggled for state: active, is-open, hidden, fadeout, selected
- elements moved to document.body to escape stacking contexts
- overlays and backdrops created dynamically in JavaScript

Practical consequence:

Refactoring HTML or CSS names without auditing the JavaScript will break behavior quickly. This folder should be reviewed whenever:

- navigation markup changes
- consent markup changes
- modal markup changes
- service card data attributes change
- side-menu structure changes


====================================================================
8. Operational Risks and Maintenance Notes
====================================================================

Highest-priority concerns:

- Home_Java.js duplicates and diverges from the modular implementation.
- 05_Flyout_Calendar.js uses placeholder availability data and hardcoded time slots.
- Navigation and side-menu logic depend on fragile DOM structure and CSS layering.
- Some modules assume required elements exist and attach handlers without defensive checks for every element.

Recommended maintenance priorities:

1. Decide whether Home_Java.js is still needed.
2. Consolidate flyout ownership between JS_Navigation.js and 04_Flyout_Panel.js.
3. Connect appointment availability to a real backend source.
4. Add stronger guardrails and console diagnostics for missing DOM requirements.
5. Move inline styling responsibilities out of JavaScript where practical.


====================================================================
9. Guidance for Future Engineers
====================================================================

If you are modifying this folder, use the following approach:

- Start in JS_Init.js to understand how the page is assembled.
- Change the modular file that directly owns the behavior.
- Avoid adding new behavior to Home_Java.js unless you have confirmed that a page still depends on it.
- Treat selectors and relative component paths as part of the module contract.
- When changing navigation, side menu, or modal behavior, verify both desktop and mobile interactions.
- When changing anything related to appointment booking, verify both the calendar UI and the flyout shortcut path.

If the long-term goal is maintainability, the next major cleanup should be removal or controlled retirement of Home_Java.js.
